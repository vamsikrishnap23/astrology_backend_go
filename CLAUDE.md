### Startup (`cmd/server/main.go`)
1. Resolve `EPHE_PATH` -> `ephemeris.Init` (checks dir exists and `sepl_18.se1` + `semo_18.se1` present; fatal otherwise; no Moshier fallback allowed).
2. `middleware.InitAuth()` (DB connect + ping is `log.Fatalf` on failure; key load).
3. Registers `/health` (public, `{"status":"ok"}`), `/api/` (auth-wrapped `ServeMux`), `/` (static file server on `./static`, relative to CWD).
4. `http.ListenAndServe` on default mux. No graceful shutdown, no CORS headers set anywhere (the OPTIONS bypass in auth just forwards to the mux, whose handlers reject non-POST with 405 — **TODO: verify** how the frontend deals with CORS/preflight; maybe a proxy).

## API

All endpoints under `/api/`, all **POST** with JSON body (other methods -> 405 `Method not allowed`), all require `Authorization: Bearer <Supabase JWT>` whose `email` claim exists in the Postgres `approved_users` table (401 missing/invalid token, 403 not approved). Errors are plain-text via `http.Error`, not JSON. Success is JSON, no envelope.

Most take the standard **BirthInput** (`domain.BirthInput`, `internal/domain/models.go`; documented in `docs/payload_birth_input.md`):
`name, date_of_birth "YYYY-MM-DD", time_of_birth "HH:MM:SS", place_of_birth, latitude, longitude, timezone (decimal hours offset, e.g. 5.5), ayanamsa, house_system, horary_number (optional 1..249)`.

## Astrology / astronomy conventions

- **Library**: Swiss Ephemeris through `github.com/tejzpr/go-swisseph` (local fork in `./go-swisseph`, cgo). Data files `ephe_data/*.se1` only (1800-2399); outside that range planet calc errors out rather than falling back to Moshier (`planets.calculateSinglePlanet` checks `FlagSwieph`).
- **Zodiac**: Sidereal. Sidereal lon is computed manually as `tropical - ayanamsa` (mod 360), deliberately NOT using `FlagSidereal` (comment says ~4 arcsec difference). Both tropical and sidereal longitude are returned.
- **Ayanamsa** (`ephemeris.GetAyanamsaMode`, case-insensitive): lahiri / "true chitrapaksha" (SE Lahiri, not SE TrueChitra), raman, krishnamurti/kp, kpnew/krishnamurti-senthilathiban (`SidmKrishnamurtiVP291`), fagan-bradley, yukteshwar, j.n. bhasin, true revati, true pushya. **Unknown/empty -> Lahiri silently.** README mentions Raman and Fagan/Bradley only partially.
- **House system** (`GetHouseSystemCode`): placidus (default), koch, porphyry, regiomontanus, campanus, equal, whole sign, sripati. **Unknown/empty -> Placidus silently.** Cusps are computed tropical then ayanamsa subtracted. Several endpoints (BTR, rasi transit) hardcode Placidus.
- **Horary (KP 1-249)**: if `horary_number` in 1..249, `houses.CalculateHouses` finds a "phantom" JD (`findPhantomJD`: scans +-0.5 d in 0.02 d steps for the ascendant crossing nearest real time, then bisects) so the ascendant equals the number's start (`houses/table_249.go`). Returns an error if no crossing is found. Only houses use the phantom time; planets use real time. Covered by `TestHoraryAscendantMatchesTable` and `TestHoraryPolarNeverSilentlyWrong`. Details and measurements: `docs/horary_phantom_jd.md`.
- **Nodes**: Rahu = Mean Node always; Ketu = Rahu + 180. `CalculationConfig.NodeMode` exists but is unused.
- **Planets returned**: Sun, Moon, Mars, Mercury, Jupiter, Venus, Saturn, Uranus, Neptune, Pluto, Rahu, Ketu (outer planets included in `/api/chart`).
- **Combustion**: computed on sidereal longitude difference from Sun with hard-coded orbs (Moon 12, Mars 17, Mercury 14/12 retro, Jupiter 11, Venus 10/8 retro, Saturn 15).
- **Retrograde**: `speed < 0`.
- **Nakshatra**: 27 x 13deg20', pada = quarter; KP lords through `tables.GetKPLords` (sub, sub-sub, up to 5 levels). Nakshatra/lord name arrays are copy-pasted in houses.go and planets.go (and probably elsewhere).
- **Time**: input local date+time + decimal tz offset -> `time.Parse("2006-01-02 15:04:05")` treated as UTC, then subtract offset (`astronomy/time.ParseLocalToUTC`). **No IANA timezones, no DST handling** — the client must send the correct offset for that date. Julian Day is UT via `swisseph.Julday` (Gregorian). `JulianDayTT` field in context is declared but not populated by handlers (**TODO: verify**).
- **Dasha**: Vimshottari, year = 365.2425 days, from Moon sidereal longitude.
- **Progression**: secondary, 1 day = 1 tropical year (365.242190402), same natal location.
- **Panchang**: tithi/nakshatra/yoga/karana boundaries by bisection; sunrise/sunset with `swisseph.RiseTrans` (Sun = upper limb + refraction, Moon = disc centre, no refraction — "Drik Panchang" methodology per code comment). Panchang handlers call `CalculationContext` without UTCTime/Ayanamsa set.
- **Concurrency**: global `ephemeris.Mu` sync.Mutex guards all SE calls; each calculation re-calls `SetEphePath`/`SetSidMode` (thread-local state in C lib). Any new SE call must take `ephemeris.Mu` and set path/sid mode first. Note `swisseph.SetSidMode` is global per call so mixing ayanamsas relies on this lock.

## Calculation reference (read from code, 2026-10-15)

Shared pipeline for most endpoints: `ParseLocalToUTC` -> `UTCToJulianDay` -> `planets.CalculatePlanets(ctx)` (also sets `ctx.Ayanamsa`) -> `houses.CalculateHouses(ctx)` -> `tables.GenerateTables(planets, cusps)` -> feature logic. `CalculatePlanets` must run before anything reading `ctx.Ayanamsa`.

### Core astronomy (`internal/astronomy`)
- **planets.go**: `CalcUT(jd, id, FlagSwieph|FlagSpeed)` for tropical lon/lat/dist/speed; second call with `FlagEquatorial` for declination. Sidereal = `tropical - ayanamsa`. `setDMS` derives sign/deg/min/sec, nakshatra (floor(lon/13.3333)), pada, plus Pushkaramsa/Bhaga, Baaladi avastha, Mrityu bhaga. Post-pass sets `Combust` and `AvasthaMood` (Deeptadi; combust => "Kopa"). Rahu/Ketu have no mood and are never combust.
- **houses.go**: `HousesEx(jd, 0, lat, lon, code)` returns tropical cusps; each cusp `- ayanamsa`. Asc = Points[0], MC = Points[1]. Cusp nakshatra/pada/lord computed inline (duplicate of planets.go logic). Horary: see above; table built in `init()` of `table_249.go` by splitting 27 nakshatras x 9 sub-lords at sign boundaries (=249 rows; each sub span = years/120 x 13deg20').
- **time.go**: `DecimalToDMS` normalises 0..360 and returns sign name + deg/min/sec-in-sign (seconds are float). `JulianDayToUTC` truncates seconds (no rounding).
- **retrogrades.go**: daily stepping of `speed`; sign change -> `findStation` bisection on speed (50 iters). Handles ranges that start/end inside a retrograde by sweeping outward 1 day at a time (unbounded `for` loops — would hang only if ephemeris never changes sign). Planets: Mercury, Venus, Mars, Jupiter, Saturn. Times formatted in request timezone offset.

### House assignment (`tables.GenerateTables`)
Planet's house = the cusp interval `[cusp_i, cusp_{i+1})` it falls in (cusp = house START, wrap handled). This is cusp-based (KP/Bhava-Chalit style), NOT sign-based; the sign-based "whole sign" house is only used in other modules (manglik, gochar, shadbala kendradi, matchmaking) via `(planetSign - refSign + 12) % 12 + 1`. `isNearBoundary` in tables.go is unused.
Occupants list on each house comes from the same assignment.

### KP (`tables/kp.go`, `internal/astrology/kp`)
- `GetKPLords(lon)` returns sign lord, star lord, sub, sub-sub, sub-sub-sub using proportional Vimshottari subdivision (years/120 of the parent span), with `1e-12` epsilons at boundaries. Note the returned names are `sl, nl, ssl, sssl, ssssl`; `TablePlanet.SubLord` = 3rd value, `SubSubLord` = 4th, `SubSubSubLord` = 5th.
- Significators (A/B/C/D): A = house occupied by the star lord, B = own house, C = houses owned by star lord, D = houses owned by the planet. "Owned" = houses whose cusp *sign lord* is that planet (cusp-sign based, so Rahu/Ketu own nothing). Four-step: planet, star lord, sub lord, star lord of sub lord; each step lists B+D (occupied+owned) houses, deduped and sorted.
- Ruling planets: asc star/sign/sub lord, Moon star/sign/sub lord, weekday lord (from the *local* calendar date via `time.Parse`, not from sunrise), then Rahu/Ketu appended as "node agents" for any non-node ruling planet if node shares its sign, sign-lord or star-lord. Duplicates intentionally kept.

### Dasha (`dasha/vimshottari.go`)
Moon sidereal lon -> nakshatra -> balance = remaining fraction x lord's years. Theoretical start = birth - elapsed fraction x years. Walks 9 mahadashas from start and keeps those ending after birth; nested antar/pratyantar/sookshma (4 levels) generated by `years_parent x years_lord / 120`, pruned to those ending after birth. Year length 365.2425 days via `time.Duration` (nanosecond truncation, float). 120-year cycle only (no second cycle).

### Panchang (`internal/astrology/panchang`)
- Tithi: `(moon - sun) mod 360 / 12` using TROPICAL longitudes (difference is ayanamsa independent). Karana = same angle / 6 over 60 slots (idx 0 Kinstughna, 57-59 fixed Shakuni/Chatushpada/Naga, others cycle 7 movable). Yoga: `sun+moon` using `FlagSidereal` (so depends on `SetSidMode` having been called), /13.333. Nakshatra: moon with `FlagSidereal`. NOTE: here sidereal comes from SE's flag, unlike planets.go (manual subtraction).
- Boundaries: `findElementBoundaries` bisects +-2.5 days around `jd` for the start/end angle (50 iters, tolerance 1e-6 deg). `getTimeline` iterates elements by jumping to `EndJD + 0.001`.
- Sun rise/set: `RiseTrans` from local midnight JD (upper limb + refraction, `BitDiscCenter|BitNoRefraction` for Moon). Solar noon = midpoint of rise/set (not true transit).
- Rahu kalam/Yamaganda: day split in 8 parts, slot indices by weekday tables `rahuMap`, `yamaMap`. Durmuhurtam: weekday-keyed 1/15-of-day muhurtas (night ones use `1 - dayDur` approx.). Varjyam/Amrita: per-nakshatra starting-ghati lookup tables, 4-ghati length, as fraction of the nakshatra's duration.
- Vara = Gregorian weekday of the local date (day starts at midnight, not sunrise, in panchang; Kala Bala dina uses sunrise-based weekday).
- Telugu calendar: ayana from sun sidereal (270-90 = Uttarayana); masam via previous/next amavasya sun sign (amanta; same sign at both = Adhika, name = next sign), rutu = masam/2, samvatsara via Shaka year approximation (March/April boundary uses masam index). `calcSunSidereal` uses `FlagSidereal` too. Sensitive; **TODO: verify** vs a reference calendar around Ugadi.

### Vargas (`vargas/rules.go`, `vargas.go`)
Registry of rule structs (`Name/Division/Calculate(lon) -> {SignIndex, LongitudeInDivision}`) for D1,2,3,4,7,9,10,12,16,20,24,27,30,40,45,60,150. Notable: D2 is Parashari Hora (Leo/Cancer only); D9 uses continuous 3deg20' parts mod 12 (equivalent to classic navamsa); D30 unequal degrees (5/5/8/7/5 odd, 5/7/8/5/5 even); D60 starts from the base sign; D150 (Nadiamsha) uses a movable/fixed/dual start. Pushkara/Baaladi/Mrityu extras are computed only for D1 and D9 (pointer fields => omitted in JSON otherwise). Vargas rebuild asc longitude from the house table (sign+deg+min+sec). Shadbala passes a single-cusp house list (`{House 1: asc}`) into `GenerateTables`/`CalculateVargas` — works because only ascendant is needed.

### Shadbala (`shadbala/`) — unit: virupas; rupas = total/60
- Sthana = Uchcha (arc from debilitation point / 3) + Saptavargaja (D1,2,3,7,9,12,30 relation points: MT 45, own 30, adhimitra 22.5, mitra 15, sama 7.5, shatru 3.75, adhishatru 1.875; uses panchadha maitri = natural + temporary-in-D1) + Ojayugma (15+15) + Kendradi (60/30/15) + Drekkana (15). Uses Moolatrikona by SIGN only (no degree limits).
- Dig: arc from zero-power point / 3 (Sun/Mars = MC, Jup/Merc = Asc, Moon/Venus = IC, Saturn = Desc).
- Kala: Nathonnatha (hours from noon/midnight x 5), Paksha (moon-sun elongation/3, doubled for Moon), Tribhaga (1/3 of day/night), Ayana (declination based, Sun x2), Dina (45 for weekday lord), Hora (60 for hora lord). **Varsha, Masa, Yuddha are hard-coded 0** ("Simplified for now"). Hora uses unequal day/12 and night/12 horas.
- Cheshta: Sun/Moon = Ayana bala; retrograde = 60; everything else direct = 30 (placeholder, not the classical speed-based formula).
- Naisargika: fixed table. Drik: benefic minus malefic aspect values /4 using custom `getAspectValue` (special aspects for Mars/Jupiter/Saturn); Moon & Mercury always treated benefic.
- Minimum rupa requirements table (Sun 6.5, Moon 6, Mars 5, Merc 7, Jup 6.5, Ven 5.5, Sat 5). **TODO: verify** classical correctness of simplifications before relying on totals; see `docs/source-validation/shadbala.md`.

### Other modules
- **Ashtakavarga**: 7 planets + Ascendant contributors from `rules.go` (BPHS tables); counts bindus per sign, no reductions (trikona/ekadhipatya shodhana not implemented). SAV = sum.
- **Bhava Chalit**: tables house assignment + raw cusps; no bhava madhya/sandhi computed.
- **Jaimini**: 7 chara karakas ranked by degree-in-sign descending (Rahu excluded; ties broken by Sun..Saturn order). Response lists all planets with `karaka` set only on the 7.
- **Manglik**: Mars house from Asc, Moon and Venus in {1,2,4,7,8,12}; many cancellation rules (own/exalt/debil, Jupiter/Moon conjunct/aspect, benefic in lagna, sign-house exceptions, exempt Moon nakshatras). Status: Non-Manglik / Cancelled Manglik / Partial (not from asc) / High. "Cancelled" is true if ANY rule fires, including the debilitated-Mars rule.
- **Gochar (transits)**: house from natal Moon (sign-based); good-house + Vedha table, Vama Vedha built by inverting it. Sun/Saturn and Moon/Mercury do not obstruct each other. Rasi-transit endpoint fakes the Moon at mid-sign.
- **Upcoming ingress**: steps 1 day (0.1 for Moon) until the sidereal sign changes (cap 2000 days), then 50-iter bisection; handles retrograde back-crossings. Rahu/Ketu use Mean Node. Result in UTC RFC3339.
- **Progression**: `progressedJD = natalJD + (targetJD - natalJD)/365.242190402`; progressed planets+houses at natal location; aspects within 1 deg orb (conj/sextile/square/trine/quincunx/opposition) vs natal planets and cusps (cusp-cusp skipped; Neptune/Pluto excluded from progressed side only).
- **Matchmaking**: Moon position from raw `CalcUT` minus `ctx.Ayanamsa`; kootas: Varna 1, Vashya 2, Tara 3 (1.5 each direction, with Anu-Janma/Eka-nakshatra/Revati/Sama-saptama exceptions), Yoni 4, Graha Maitri 5, Gana 6, Bhakoot 7, Nadi 8 (raw + effective after cancellations); Rajju, Lagna kootami, Kala Sarpa, Mruga Vairam, Ashubha Kurpu, individual risk checks are extras from a "Telugu book" (`tables.go` header `classical-guna-milan-v1`). `Maximum: 36` on the main total. **TODO: verify** exact scoring beyond the structure above; matchmaking.go is ~1000 lines of rules.
- **BTR** (Nadi Tatwa): LMT = clock - (tz*15 - lon)*4min; sunrise (Hindu rising) vs 06:00 offset shifts time; 480 rows of 3 minutes; tatwa/gender by weekday group and half-cycle direction; row planet from 9-planet cycle offset by sign modality and weekday lord; candidates scanned in a +-window (default -10/+5 min) and scored (gender match +5, star lord match +5). `btr/tatwa.go` (`CalculateTatwa`) appears unused by `btr.go` (**TODO: verify**).

### Calculation quirks worth knowing before changing code
- Sidereal source is inconsistent: manual (`tropical - ayanamsa`) in planets/houses/transit/matchmaking vs `FlagSidereal` in panchang nakshatra/yoga/sun. Differences are arcseconds.
- `CalcUT` flags exclude `FlagNoNutation`/true-vs-mean specifics; default SE behaviour (apparent positions).
- Nodes use MeanNode in every module (planets, upcoming ingress), `NodeMode` unused.
- Nakshatra/lord tables duplicated in: planets.go, houses.go, tables.go, panchang, matchmaking, dasha, kp; sign names/lords duplicated in ~8 packages. A refactor should centralise but behaviour must be preserved.
- Panchang/BTR build "start of local day" with `time.Parse` + `.UTC()`/fixed zone; BTR parses date as UTC midnight and ignores timezone when asking for sunrise (**TODO: verify** effect for non-IST offsets).
- `getWeekday` in BTR truncates minutes (uses hour only) when converting JD to local weekday.
- Several functions ignore errors (`_`), e.g. BTR's `planets.CalculatePlanets`/`CalculateHouses`, matchmaking asc calc, panchang date parse.

### Sidereal derivation inconsistency (measured 2026-10-15)
Two ways of producing sidereal longitude coexist:
- **Manual**: `CalcUT(jd, body, FlagSwieph)` (tropical, true equinox incl. nutation) minus `GetAyanamsaUT(jd)`. Used in `planets.go`, `houses.go`, `transit/upcoming.go`, `matchmaking/nakshatra.go`.
- **`FlagSidereal`**: SE applies its own sidereal transform. Used in `panchang/{nakshatra,yoga,telugu_calendar}.go`.
Measured difference for the Moon (same ayanamsa mode): -1.3" (1950), -12.7" (1985), -15.9" (2000), -3.8" (2024), -15.1" (2040): it varies with date, up to ~16", consistent with nutation in longitude (not proven). The code comment "~4 arcsec" is just the 2024 value.
Consequence: `/api/chart` Moon and `/api/panchang` nakshatra can disagree near a nakshatra/pada boundary; `GetKPLords` sub-sub-sub spans can be as small as ~6", so the 5th KP level can differ. Decide one convention (and the matching KP/Lahiri expectation of the reference software) before changing either side.
